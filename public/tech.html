Production integration plan

e-Laya inside the eGovPH Super App

Six Mini-Apps, rendered as WebViews, authenticated through the host.

e-Laya is designed as a module within the eGovPH Super App — not a standalone application. Each surface loads as a Mini-App inside the host's in-app browser, sharing the user's authenticated session and presenting a native feel through a lightweight PWA shell. Below is how that integration works.

Integration model: Mini-App / WebView

The eGovPH Super App hosts each e-Laya surface as an embedded WebView. The host controls authentication and navigation; each Mini-App renders a focused, role-specific interface.

Super App

eGovPH host application — manages the user session, native navigation bar, and role-based routing. The user never leaves the Super App shell. Each e-Laya surface is loaded as a Mini-App route within the host.

⬇ WebView bridge (postMessage)
Mini-App

Six independent WebView surfaces — Kiosk, Family, Cases, Sessions, Verify, Custody. Each is a React/Next.js PWA bundle loaded on demand. The host passes auth tokens via postMessage; no separate login screen.

⬇ HTTPS (API proxy)
eGovPH APIs

Seven government services — SSO, eVerify, Face Liveness, eGov AI, eMessage, PSGC, and eGovChain. All calls route through a server-side API proxy that keeps credentials off the client.

⬇ eGovDX
Agency systems

Existing government systems — BJMP, DSWD, PAO, courts. e-Laya reads from and writes back to these systems through the eGov Data Exchange layer, never replacing them.

Host-to-WebView authentication bridge

The user authenticates once in the Super App. The host passes the session to each Mini-App through a structured postMessage protocol — no second login, no embedded credentials in URLs.

eGovPH Super App (Host)

User is authenticated via eGov SSO within the host. User taps "My Family" in the Super App.

// Host sends session and role to the WebView
webView.postMessage({
  type: 'egov-session',
  token: 'eyJhbG...',
  role: 'guardian',
  surface: 'family',
  locale: 'fil'
}, '*');
→

Mini-App WebView (e-Laya)

Mini-App receives the session and renders its surface. No login screen is shown; the user lands directly on their content.

// Mini-App listens for the host message
window.addEventListener('message', (e) => {
  if (e.data.type === 'egov-session') {
    initSurface(e.data);
  }
});

Security note: The token passed to the WebView is a short-lived, surface-scoped access token — not the user's primary SSO session token. The Mini-App uses it to authenticate API proxy calls and validate its role. Token lifetime is bounded to the WebView session duration.

Frontend architecture

Each Mini-App is a lightweight Next.js PWA bundle. Surfaces share a common component library and design system but are built and deployed independently — no single-page app monolith.

Shared layer

  • elaya-ui — shared React component library (cards, forms, banners, status chips)
  • elaya-store — client-side state with localStorage persistence + cross-tab sync
  • elaya-api — typed API client for the proxy layer with offline queue
  • elaya-auth — WebView bridge adapter for host session messages

Per-surface bundles

  • Each surface is a separate Next.js route group or page
  • Code-split at the surface boundary — no surface loads another's components
  • PWA service worker enables offline operation with indexed-db sync queue
  • WCAG 2.1 AA compliance enforced at the component level

Authentication flow

Host-to-WebView token bridge

Host passes { token, role, surface, locale } via postMessage. Mini-App validates the token against the API proxy, establishes a session, and renders the appropriate surface. No redirect-based login, no OAuth popups inside the WebView.

postMessageSSOtoken bridge

Offline resilience

Service worker & IndexedDB queue

A service worker caches surface shells and API responses. Writes (welfare checks, attendance) are queued in IndexedDB and flushed when connectivity returns. The UI remains fully interactive offline — no blank screens, no spinners that never resolve.

PWAservice workerIndexedDB

Role-based routing

Role-gated Mini-App access

The Super App determines which surface the user sees based on their SSO role. A guardian sees the Family Mini-App; a PAO lawyer sees Cases. The host never loads a surface the user is not authorised to access — the route decision happens at the Super App level, not inside the WebView.

SSO roleshost routersecurity

eGovPH design system & 44px WCAG

The design system (elaya.css tokens) matches eGovPH's visual language. Touch targets are minimum 44x44px (WCAG 2.1). The WebView is configured with transparent navigation so the Super App's native bar surfaces above Mini-App content. Font sizes, radii, and spacing follow eGovPH's published tokens exactly.

Once-only data entry

Inter-surface data propagation

Data captured by one surface is available to all others through the shared API layer. A welfare check logged in Custody surfaces in Family. An identity determination in Verify propagates to Cases and Sessions. No officer re-enters what another officer has already entered.

eGovDXdata propagationshared API

Surface isolation

Independent WebViews & memory space

Each Mini-App is an independent WebView — separate DOM, separate memory, separate network context. A crash or memory leak in one surface cannot affect another. The Super App can unload idle Mini-Apps and reload them on demand without data loss (state is persisted through elaya-store).

isolationPWA bundlesmemory safety

Production tech stack

Every layer is chosen to match the eGovPH engineering team's tooling and to satisfy government infrastructure requirements. No new framework is introduced into the ecosystem.

eGovPH API integration

Seven government services integrated through a common API proxy. The proxy enforces credential isolation, response caching, and structured error handling — every call returns { ok: boolean, data?: ..., error?: ... }.

eGov SSO

Authentication & role gating

Establishes who the user is and what role they hold. In the Mini-App model, SSO is handled by the Super App host; the WebView receives a pre-authenticated session token scoped to its surface. The partner JWT never reaches the browser.

eVerify

National ID verification

QR code scanning, demographics lookup, and liveness binding for identity resolution. The PhilSys Card Number is never persisted — only a salted SHA-256 hash crosses the API boundary. Demographics are display-only and discarded on navigation.

identityage determination

Face Liveness

Anti-spoofing biometrics

Session creation and result retrieval proxied server-side. The 95.0 confidence threshold is enforced on the server — a compromised client cannot lower it. The biometric check itself runs on a government-hosted page, not inside the Mini-App.

biometricsanti-spoofing

eGov AI

Translation, OCR, speech, laws

Four capabilities: nine-language translation (UI pre-baked, dynamic content via API), speech synthesis for read-aloud, document extraction for age proof from birth certificates, and laws lookup for rights and legal provisions.

translationOCRTTS

eMessage

SMS notifications

Delivers welfare updates, hearing reminders, and programme notifications via SMS. Numbers are normalised to E.164 with a 60-second deduplication window. The channel that reaches families on basic phones with no data connection.

SMSnotifications

PSGC (eReport)

Geographic hierarchy

Region → province → city → barangay resolution for address lookups and programme localisation. Slow-changing data cached aggressively at the proxy and service worker layers. Ensures "a programme near me" maps to a real, standardised administrative area.

geographyaddress

eGovChain

Tamper-evident receipts

Attendance records and welfare confirmations produce a canonical-JSON SHA-256 receipt hash. In production with a writable chain, these receipts would be anchored on-chain — a judge or auditor could independently verify that a welfare check occurred at a specific time, independent of the database.

blockchainaudit

Security & privacy architecture

No PII, no biometric, no credential reaches the Mini-App client. Enforced structurally, not by policy.

API proxy isolation

Server-side credentials

All government API secrets are environment variables on the server. The Mini-App calls /api/* endpoints; it never holds an API key, partner secret, or access token. Extraction from client code is impossible because they do not exist there.

API keysenvironment varsisolation

PCN never stored

Salted SHA-256 hashing

The PhilSys Card Number is hashed with a salt server-side and only the hash crosses the response boundary. Full demographics are returned for display only and discarded when the WebView is closed — never persisted in any database or localStorage.

PhilSysSHA-256privacy

Server-side threshold

95.0 confidence check

Face liveness confidence threshold (95.0) is enforced in the proxy function. A compromised Mini-App cannot lower it. The biometric check runs on a government-hosted page, never inside e-Laya code.

biometrics95.0 thresholdserver-enforced

Scoped WebView tokens

Short-lived access JWT

The token the host passes to the WebView is a short-lived, surface-scoped access token — not the user's primary SSO session. The Mini-App can only call its authorised API proxy routes. Token lifetime is bounded to the WebView session.

token scopeJWTsession bound

Data proportionality

Strict surface scoping

Each surface collects only what its stakeholder needs. The Kiosk Mini-App shows case status without full identity. The Family Mini-App shows welfare without accessing the case file. No Mini-App carries another surface's code or data.

data privacyleast privilegescoping

Audit trail

Tamper-evident operations

Every welfare check, identity determination, and attendance record logs who performed the action, when, from which device, and under which SSO session. This creates a tamper-evident chain of accountability for all operations.

Integration with existing agency systems

e-Laya does not replace any agency system. It is an additive person-tracking layer that reads from and writes back to existing systems through the eGov Data Exchange (eGovDX).

BJMP

Bureau of Jail Management and Penology

Reads facility rosters and commitment records — never replaces the system that creates them. Writes welfare check data that BJMP can consume through eGovDX.

rosterswelfare checkseGovDX

DSWD

Dept. of Social Welfare and Development

Provides a digital interface for attendance logging that social workers currently do on paper. Pushes attendance records back to DSWD's case management systems.

attendancesocial workersCICL cases

PAO

Public Attorney's Office

Supplies a prioritised, ranked caseload view pulling from court hearing data and e-Laya's own person records. Lawyers record outcomes that flow back to the family surface.

caseloadhearing datesPAO lawyers

Courts

Supreme Court eCourts System

Reads hearing dates and case stages read-only through the eCourt integration layer (when available via eGovDX). Never writes to or modifies court records.

read-onlyeCourtdockets

Once-only data entry principle: A welfare check confirmed by a BJMP officer in the Custody Mini-App is visible to the guardian in the Family Mini-App and to the PAO lawyer in Cases — without anyone re-entering it. A social worker logging attendance in Sessions does not need to separately report it to the court. The system carries the record across surfaces through the shared API layer.
